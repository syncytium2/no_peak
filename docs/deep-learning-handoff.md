# Handoff: a learned pulse detector for no_peak

**Status:** proposal, nothing built yet.
**Written:** 2026-08-08, against no_peak v0.2.0.
**Audience:** whoever picks this up next — a person, or an agent with this repo.

---

## 1. The gap

While assembling the About page we checked the literature for a deep-learning
pulse detector for serial hormone assays and did not find one. Adjacent ML work
exists (hormone trajectory prediction, cycle-phase classification from
wearables) but nothing that identifies pulses in a concentration time series the
way CLUSTER, PULSAR, AutoDecon, or hormoneBayes do.

**First task for whoever picks this up: re-run that search.** The claim is
current as of August 2026 and is the entire premise of this document. If someone
published one in the meantime, read it before writing code — and the right move
may be to port or wrap theirs rather than train our own.

## 2. Why the gap exists (read this before assuming it's an oversight)

It is not that nobody thought of it. Four things make this task hostile to the
standard deep-learning recipe, and any credible proposal has to answer all four.

1. **There are no labels.** Real hormone series have no ground truth. Nobody
   knows where the pulses "really" are — that is the whole problem. You cannot
   assemble a labelled corpus by annotating real data, because the annotation
   would just be some other algorithm's output, and you would be training a
   student to imitate a teacher whose errors you inherit.
2. **The data are tiny.** A study might yield dozens of series of ~100 points
   each. That is kilobytes. Sharing is limited by IRB and consent, so there is
   no ImageNet here and there will not be one.
3. **The field values inspectability.** CLUSTER survives at forty because you
   can explain it in two sentences and audit every decision. A black box that
   reports "pulse here, trust me" will not be adopted, and reviewers will be
   right to push back.
4. **Uncertainty is already solved better elsewhere.** hormoneBayes and the
   Bayesian deconvolution family give calibrated posteriors from mechanistic
   models. "Neural net gives a point estimate" is a step backwards from that.

## 3. The proposed framing

Not "a neural network that detects pulses." Instead:

> **Amortized simulation-based inference.** Train a network on data generated by
> the same mechanistic model the field already accepts, so that it learns to
> approximate the Bayesian posterior over pulse times — then run that
> approximation in milliseconds, in the browser, instead of running MCMC.

This framing answers all four objections above:

- **Labels** come free: the simulator knows where it put the pulses.
- **Data** is unlimited for the same reason.
- **Inspectability** survives because the generative model is the familiar
  secretion-convolved-with-clearance model, not a learned black box; the network
  approximates inference *in* that model rather than replacing it. Ship the
  simulator alongside the weights and anyone can audit what it was trained on.
- **Uncertainty** is the output, not an afterthought: the network emits a
  per-timepoint posterior probability of pulse onset, which is exactly the thing
  a point-estimate detector cannot give you.

The value proposition is therefore **not** "more accurate than CLUSTER." It is
"posterior uncertainty at CLUSTER's speed, running client-side." If the accuracy
also improves in the low-amplitude / high-noise regime where CLUSTER is
conservative, that is a bonus to measure, not the headline to promise.

## 4. Hard constraints from this project

- **It must run client-side.** no_peak's whole identity is that data never
  leaves the browser. A model behind an API would break the one promise the app
  makes. Budget: a few hundred KB of weights, CPU inference via
  `onnxruntime-web` or similar, well under a second for a 200-point series. This
  is easily achievable at this sequence length and rules out anything large.
- **It must consume the error channel.** Per-sample assay precision is what
  makes CLUSTER honest. Feed it as an input channel, not an afterthought — a
  model that ignores measurement error will confidently call noise.
- **It must degrade to CLUSTER.** Ship it as an additional Implementation
  option next to `igor` and `fortran`, never as a silent replacement. Existing
  results must stay bit-identical.
- **It must handle irregular sampling.** Condition on Δt per interval; do not
  assume a fixed grid.

## 5. What already exists here to build on

- [`src/demo.ts`](../src/demo.ts) — already the nucleus of the simulator:
  baseline, exponential clearance (45 min half-life), additive pulses, ~7% CV
  noise, seeded PRNG. Generalize this into the training generator.
- [`src/core/cluster.ts`](../src/core/cluster.ts) — the baseline to beat, and a
  labeler for sanity checks. Both variants available.
- [`scripts/run_csv.ts`](../scripts/run_csv.ts) — batch runner; extend it to
  score a whole synthetic corpus.
- [`data/extracted/`](../data/extracted/) — real GnRH/LH series with genuine
  per-sample error columns. Small, but the right shape for the sim-to-real
  check and for calibrating the noise model.
- The Igor panel settings in `data/extracted/igor_panel_settings.txt` record
  parameters from a real analysis session — useful priors for what humans
  actually choose.

## 6. Plan

### Phase 0 — decide whether to proceed (about a day)
Re-run the literature search (§1). Write down what would make this *not* worth
doing. Then read Veldhuis & Johnson 1994 (*Methods Enzymol* 240:377–415) on
simulation-based testing of pulse detectors — the field has a fifty-page
opinion on how to generate synthetic series and score detectors against them,
and matching that methodology is most of what makes this credible.

### Phase 1 — the simulator (the real work)
Everything downstream is only as good as this. Deliverable: a documented,
seedable generator producing `(times, values, errors, true_onsets)`.

Must span, with priors drawn from the literature rather than invented:
half-life, basal secretion, pulse mass and shape, inter-pulse interval
distribution (including non-stationary drive), sampling interval and duration,
assay CV as a function of concentration (low-concentration CV blow-up is where
detectors actually fail), missing samples and outliers, and a slowly varying
baseline — Carlson 2013 found that ignoring a circadian baseline biases every
method's parameters, so it must be in the training distribution.

**Validation gate:** a domain expert should be unable to reliably distinguish
simulated series from real ones, and CLUSTER's sensitivity/false-positive rates
on the simulated corpus should land near its published values (~80% / ~1% in
the AutoDecon comparison). If CLUSTER behaves differently on your synthetic data
than it does in the literature, the simulator is wrong — fix it before training
anything.

### Phase 2 — baselines on the benchmark
Before any model: score CLUSTER (both variants), and PULSAR Otago if you can
script it, on the frozen synthetic benchmark. Publish that table in the repo.
Half the value of this project is a shared benchmark, independent of whether the
network works.

### Phase 3 — the model
Start small and boring: a dilated temporal convolutional network or a small
U-Net over the sequence, inputs `[value, error, Δt]` per step (consider also
value/error as an explicit channel — it is CLUSTER's own statistic), output a
per-timepoint onset probability. Target well under a million parameters. Train
with a proper scoring rule so the probabilities mean something; check
calibration explicitly (reliability diagram), because a miscalibrated
"posterior" is worse than no posterior.

Only reach for a transformer or a normalizing-flow posterior if the simple thing
demonstrably plateaus.

### Phase 4 — honest evaluation
- Sensitivity **and** false-positive rate, reported together, always. The
  CLUSTER-vs-AutoDecon comparison is instructive: higher sensitivity bought with
  6× the false positives is not a free win, and which side of that trade you
  want depends on the biological question.
- Calibration of the emitted probabilities.
- Sim-to-real: run on `data/extracted/`. There is no ground truth, so measure
  *agreement* with CLUSTER and characterize the disagreements case by case. Any
  disagreement is a finding to explain, not a number to average away.
- Robustness: deliberately train on one simulator configuration and test on a
  shifted one. The sim-to-real gap is the single most likely failure mode of
  this whole plan; measure it directly rather than hoping.

### Phase 5 — ship it, carefully
Fourth Implementation option. Show the probability trace as a panel beside the
t-score panel — the honest UI is "here is the model's confidence over time,"
not a binary overlay that looks as authoritative as the statistics. Record the
model version in the CSV header and PDF report exactly as `impl=` is recorded
now. Publish the simulator, the benchmark, the weights, and the training code
together; a learned detector whose training distribution is not inspectable is
not usable science.

## 7. Kill criteria

Stop and write up the negative result if any of these hold:

- The simulator cannot reproduce CLUSTER's published operating characteristics
  (Phase 1 gate). Everything downstream would be built on sand.
- On the benchmark, the model cannot beat CLUSTER on *both* axes at any
  operating point, **and** its probabilities are not well calibrated. Then it
  offers nothing CLUSTER does not.
- Sim-to-real disagreement is large and unexplainable. A detector that works on
  synthetic data and disagrees mysteriously with forty years of practice on real
  data is not publishable and not shippable.

A clean negative result here is genuinely useful to the field — it would explain
*why* the gap exists, which is currently just an observation. Write it up either
way.

## 8. Open questions

- Is onset detection even the right target? Alternatives: pulse count posterior,
  inter-pulse-interval posterior (what DynPeak and hormoneBayes optimize for), or
  full secretion-rate reconstruction. IPI may be what most users actually want.
- Should this be trained per-hormone (LH, GnRH, cortisol have different kinetics
  and pulse structure) or conditioned on half-life as an input? Conditioning is
  more useful but harder to get right.
- Is there a collaboration here rather than a solo build? The hormoneBayes group
  has the mechanistic model and the domain credibility; amortizing *their*
  posterior is a more defensible paper than inventing a parallel one, and this
  app could be the client-side delivery vehicle for it.
- Would a hybrid be better than either — the network proposing candidate pulses
  and CLUSTER's t-test confirming them, so the statistics stay auditable and the
  network only improves recall?
